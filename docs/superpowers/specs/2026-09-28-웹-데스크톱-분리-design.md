# 손글씨 인식기 웹/데스크톱 분리 설계

작성일: 2026-09-28 (KST)

## 1. 목표와 범위

현재 저장소는 PyTorch 기반 손글씨 숫자 인식기 하나가 루트에 평평하게 놓여 있다.
이를 두 갈래로 나눈다.

- **`desktop_version/`** — 기존 PyTorch 코드 전부. 학습과 추론을 모두 담당한다.
- **`web_version/`** — 외부 라이브러리 없이 순수 자바스크립트로 추론하는 정적 웹 페이지.
  GitHub Pages 에 그대로 올라간다.

**웹 버전의 목적은 공유용 데모다.** URL 하나로 누구나 브라우저에서 숫자를 그려
인식해 볼 수 있게 하는 것이 1차 목표이고, 그 결과가 데스크톱 버전과 같다는 것을
수치로 증명할 수 있는 구조를 2차 목표로 둔다.

### 명시적 비목표 (YAGNI)

- 브라우저에서의 **학습**. 추론만 한다.
- **양자화**. float32 그대로 보낸다. 1.69MB 는 GitHub Pages 에서 문제가 되지 않는다.
  크기가 실제로 문제가 되면 그때 붙인다.
- WebGL / WebAssembly / WebGPU 가속. 순전파 1회 약 424만 MAC 은 평범한 JS 루프로 수 ms 다.
- 중간 특징맵 시각화 등 교육용 장치.
- 파일 업로드 인식(`predict.py` 의 웹 대응물). 캔버스 입력만 받는다.

## 2. 성공 기준

1. `web_version/` 을 정적 호스팅에 올리면 마우스·터치로 숫자를 그려 인식된다.
2. `verify.html` 이 MNIST 테스트셋 200 장에 대해 아래를 만족한다고 보고한다.
   - PyTorch 예측과 JS 예측의 **일치율 100%**
   - 로짓 최대 절대오차 **1e-3 이하**
   - 전처리 결과 28x28 픽셀의 최대 절대오차 **1 이하** (0~255 스케일)
3. `desktop_version/` 의 6개 파이썬 진입점이 이동 전과 동일하게 동작한다.
4. 루트와 두 하위 폴더에 각각 목적에 맞는 `CLAUDE.md` 가 있다.

### 2.1 오차 허용치를 0 이 아니라 위와 같이 잡은 이유

- **로짓**: float32 누산 순서가 PyTorch(BLAS)와 JS 루프에서 다르다. 같은 수식이라도
  마지막 자리에서 갈린다. 예상 오차는 1e-5 수준이며, 1e-3 은 넉넉한 상한이다.
- **전처리 픽셀**: PIL 의 LANCZOS 축소는 고정소수점 산술로 구현되어 있고 패스마다
  8비트로 반올림한다. JS 쪽은 같은 계수·같은 2패스 순서를 쓰되 배정밀도로 계산하므로
  마지막 반올림에서 1 이 차이 날 수 있다. 1 의 차이는 정규화 후 0.013 표준편차에
  해당해 예측을 뒤집지 못한다. 실제로 뒤집힌다면 1번 기준(일치율 100%)이 잡아낸다.

### 3.1 명명 규칙

**파일명은 영어, 파일 내부의 식별자와 주석은 한글.**

기존 저장소가 이미 그렇다(`model.py`, `train.py` 안에 `숫자인식CNN`, `한에폭_학습`).

한글 파일명은 퍼센트 인코딩을 타게 되고, 정적 호스팅·CDN·프록시 조합에 따라
깨지는 경우가 생긴다. 굳이 감수할 이유가 없다.

### 3.2 이동 방식

`git mv` 로 옮겨 이력을 보존한다. `__pycache__/` 는 옮기지 않고 삭제한다.

기존 파이썬 파일은 모두 `Path(__file__).resolve().parent` 를 기준으로 경로를 잡으므로,
폴더째 옮겨도 **코드 수정이 필요 없다.** `app.py` 의 `os.chdir(현재폴더)` 와
`sys.path.insert` 도 자기 위치 기준이라 그대로 동작한다.

`.gitignore` 의 `data/`, `__pycache__/` 패턴은 앞에 `/` 가 없어 어느 깊이에서든
매칭되므로 수정할 필요가 없다.

## 4. 가중치 내보내기 (`export_weights.py`)

### 4.1 BatchNorm 접기

추론 시 BatchNorm 은 앞 합성곱의 가중치·편향에 흡수할 수 있다.

```
s  = 감마 / sqrt(분산 + 엡실론)        (출력 채널마다 하나, 엡실론 = 1e-5)
W' = W * s
b' = (b - 이동평균) * s + 베타
```

이렇게 하면 **JS 쪽에 BatchNorm 구현이 아예 필요 없다.** 내보낼 파라미터도
`running_mean` / `running_var` / `weight` / `bias` 네 묶음이 사라진다.

Dropout 은 `eval()` 상태에서 항등함수이므로 내보낼 것이 없다.

접기 후 남는 파라미터:

| 레이어 | 형상 | 원소 수 |
|---|---|---|
| `합성곱1.가중치` | (32, 1, 3, 3) | 288 |
| `합성곱1.편향` | (32,) | 32 |
| `합성곱2.가중치` | (64, 32, 3, 3) | 18,432 |
| `합성곱2.편향` | (64,) | 64 |
| `전결합1.가중치` | (128, 3136) | 401,408 |
| `전결합1.편향` | (128,) | 128 |
| `전결합2.가중치` | (10, 128) | 1,280 |
| `전결합2.편향` | (10,) | 10 |
| **합계** | | **421,642** |

421,642 × 4바이트 = 1,686,568 바이트 (약 1.61 MiB).

### 4.2 `weights.bin`

위 표의 순서대로 각 텐서를 **PyTorch 기본 메모리 배치(C 순서, row-major)** 그대로
리틀엔디언 float32 로 이어 붙인다. 구분자나 헤더는 없다.

`Conv2d` 가중치는 `(출력채널, 입력채널, 커널높이, 커널너비)`,
`Linear` 가중치는 `(출력특징, 입력특징)` 이다. JS 의 인덱싱이 이 배치를 그대로 따른다.

### 4.3 `shape.json`

```json
{
  "설명": "mnist_cnn.pt 에서 BatchNorm 을 접어 내보낸 추론용 가중치 명세",
  "생성일시": "2026-09-28 14:52 (KST)",
  "정규화": { "평균": 0.1307, "표준편차": 0.3081 },
  "전체원소수": 421642,
  "레이어들": [
    { "이름": "합성곱1.가중치", "형상": [32, 1, 3, 3], "오프셋": 0,   "원소수": 288 },
    { "이름": "합성곱1.편향",   "형상": [32],          "오프셋": 288, "원소수": 32 }
  ]
}
```

`오프셋`은 바이트가 아니라 **float32 원소 단위**다. `model.js` 가
`new Float32Array(버퍼, 오프셋 * 4, 원소수)` 로 잘라 쓴다.

`정규화` 값은 `model.py` 의 `평균` / `표준편차` 를 `import` 해서 적는다.
이렇게 해서 "`model.py` 가 정규화 상수의 단일 출처" 라는 기존 원칙이 웹까지 연장된다.
웹 쪽에서 이 값을 하드코딩하지 않는다.

### 4.4 `verify_samples.json`

검증은 **전처리와 추론을 모두** 통과시켜야 의미가 있다. 그러려면 양쪽에
비트 단위로 같은 입력을 줘야 한다.

MNIST 테스트셋 앞 200 장을 다음과 같이 캔버스 입력으로 흉내 낸다.

1. 원본 28x28 (검은 배경 + 흰 글씨)
2. 255 에서 빼서 반전 → 흰 배경 + 검은 글씨 (이미지 파일 인식과 같은 모습)
3. **최근접 이웃으로 정확히 10배 확대** → 280x280

3번이 핵심이다. 10배 정수 확대의 최근접 이웃 보간은 단순한 10x10 블록 복제라
파이썬과 JS 에서 결과가 필연적으로 동일하다. 보간 방식 차이가 검증에
끼어들 여지를 없앤다. 그래서 JSON 에는 280x280 이 아니라 **원본 28x28 만 담고**,
2·3번 변환은 양쪽이 각자 수행한다. 파일 크기도 100배 줄어든다.

```json
{
  "설명": "...",
  "샘플수": 200,
  "정답": [7, 2, 1],
  "원본28x28_base64": "...",
  "기대_전처리28x28_base64": "...",
  "기대_로짓": [[0.0]]
}
```

- `원본28x28_base64` — 200 × 784 바이트
- `기대_전처리28x28_base64` — 200 × 784 바이트, `preprocess.py` 의 출력
- `기대_로짓` — 200 × 10, `forward()` 의 반환값이므로 **로그 확률**이다

base64 는 JS 내장 `atob()` 로 푼다. 외부 라이브러리가 필요 없다.

### 4.5 사용법

```bash
cd desktop_version
python export_weights.py
```

`mnist_cnn.pt` 를 읽어 `../web_version/weights/` 아래 세 파일을 덮어쓴다.
학습으로 가중치가 갱신되면 이 명령을 다시 돌려야 웹 버전에 반영된다.
이 의존 관계를 세 `CLAUDE.md` 에 모두 적는다.

## 5. 웹 추론 엔진

### 5.1 모듈 경계

네 모듈은 아래 의존 방향만 갖는다. 역방향 참조는 없다.

```
app.js ──> model.js ──> tensor.js
   └─────> preprocess.js
```

**`tensor.js` · `preprocess.js` · `model.js` 는 DOM 을 건드리지 않는다.**
이 제약 덕분에 `verify.html` 이 캔버스 없이 세 모듈을 그대로 불러 검증할 수 있다.
DOM 접근은 `app.js` 에만 있다.

ES 모듈(`<script type="module">`)을 쓴다. `file://` 로 열면 모듈 로딩과
`fetch()` 가 모두 막히므로, 로컬 확인은 `python -m http.server` 로 한다.
GitHub Pages 는 https 라 그대로 동작한다.

### 5.2 `tensor.js`

형상 정보를 들고 다니지 않는 **평평한 `Float32Array` + 명시적 차원 인자** 방식으로 간다.
텐서 클래스를 만들지 않는다. 연산이 다섯 개뿐이라 추상화가 이득보다 비용이 크다.

| 함수 | 역할 |
|---|---|
| `합성곱2차원(입력, 입력채널, 크기, 가중치, 편향, 출력채널)` | 3x3, padding=1, stride=1 고정 |
| `렐루(배열)` | 제자리 연산 |
| `최대풀링2차원(입력, 채널수, 크기)` | 2x2, stride=2 |
| `전결합(입력, 가중치, 편향, 입력수, 출력수)` | |
| `로그소프트맥스(배열)` | 최댓값을 빼는 안정화 방식 |

`합성곱2차원` 은 padding=1, stride=1, 3x3 만 지원한다. 모델이 그것만 쓴다.
일반화된 conv 를 만들지 않는 이유는 YAGNI 이며, 경계 검사를 단순화할 수 있어
더 빠르기도 하다.

`로그소프트맥스`는 `log_softmax` 와 동일하게 `x - 최댓값` 으로 안정화한 뒤
`x - 최댓값 - log(sum(exp(x - 최댓값)))` 을 계산한다. PyTorch 와 같은 수식이라야
로짓 대조가 성립한다.

### 5.3 `preprocess.js` — 인식률의 핵심

`preprocess.py` 의 단계를 순서·수치까지 그대로 옮긴다. 입출력은 DOM 이 아니라
`{ 너비, 높이, 화소 }` 형태의 단순 객체다 (`화소` 는 `Uint8ClampedArray`).

1. **회색조 변환** — PIL 의 `convert("L")` 과 같은 ITU-R 601-2 계수
   `L = (R*299 + G*587 + B*114) / 1000`, 소수점 이하 버림.
2. **배경 판단 후 반전** — 가장자리 화소(첫 행, 마지막 행, 첫 열, 마지막 열)의
   평균이 127 초과면 반전. `preprocess.py` 가 `np.concatenate` 로 이어 붙이면서
   **네 모서리를 두 번씩 세는데, 이 중복을 그대로 재현한다.** 판단이 갈리면
   전체 결과가 뒤집히므로 "더 올바른" 구현으로 고치지 않는다.
3. **글씨 영역 crop** — 밝기 > 30 인 화소의 최소 사각형.
   비어 있으면 28x28 검은 이미지를 즉시 반환.
4. **긴 변 20px 로 축소** — 비율 유지. Lanczos3 (5.4 참조).
5. **28x28 중앙 배치** — `(28 - 새너비)` 를 2로 내림 나눗셈한 위치.
6. **무게중심을 (13.5, 13.5) 로 이동** — 밝기 가중 평균으로 중심을 구하고
   정수 픽셀 단위로 평행이동, 빈 자리는 0. 이 단계를 빼면 눈에 띄게 틀린다.

#### 파이썬식 반올림

4단계의 `새너비 = max(1, int(round(너비 * 비율)))` 와 6단계의
`int(round(13.5 - 중심x))` 는 **파이썬 `round()`, 즉 짝수로의 반올림**이다.
JS 의 `Math.round()` 는 언제나 큰 쪽으로 붙으므로 `.5` 에서 갈린다.

`파이썬_반올림(값)` 헬퍼를 만들어 두 곳 모두 이 헬퍼를 쓴다. 4단계에서 1픽셀이
달라지면 이후 모든 픽셀이 어긋나므로 사소한 문제가 아니다.

### 5.4 Lanczos3 축소

**`canvas.drawImage` 로 축소하면 안 된다.** 브라우저마다 보간 알고리즘이 다르고
명세에도 고정되어 있지 않아 재현성이 없으며, PIL 결과와도 어긋난다.
"외부 라이브러리 없이 순수 JS" 요구와 별개로, 직접 구현이 유일하게
검증 가능한 선택이다.

PIL 의 `ImagingResample` 과 같은 방식을 따른다.

- 커널: `L(x) = sinc(x) * sinc(x/3)`, 지지구간 3.0
- **축소 시 커널을 늘린다**: `필터배율 = max(1, 입력크기 / 출력크기)`,
  `지지구간 = 3.0 * 필터배율`. 이 확대가 에일리어싱을 막는 부분이라 빼면 안 된다.
- 출력 픽셀마다 입력 구간의 가중치를 구하고 **합이 1이 되도록 정규화**한다.
- **가로 패스 → 세로 패스 2패스**, 패스 사이에서 0~255 로 반올림·클램프한다.
  PIL 이 uint8 이미지를 그렇게 처리하므로 순서를 맞춘다.

### 5.5 `model.js`

```
가중치_불러오기(기준경로) -> { 정규화, 레이어 }     // shape.json + weights.bin 을 fetch
숫자인식CNN.순전파(입력28x28) -> Float32Array(10)   // 로그 확률
```

순전파는 `model.py` 의 `forward` 와 같은 순서다. BatchNorm 과 Dropout 은
4.1 에 따라 생략된다.

```
28x28x1 ─합성곱1─ 28x28x32 ─렐루─ ─풀링─ 14x14x32
        ─합성곱2─ 14x14x64 ─렐루─ ─풀링─ 7x7x64
        ─평탄화─ 3136 ─전결합1─ 128 ─렐루─ ─전결합2─ 10 ─로그소프트맥스─ 10
```

**평탄화 순서가 중요하다.** PyTorch 의 `x.flatten(1)` 은 `(N, 64, 7, 7)` 을
채널 우선으로 편다 — 인덱스는 `채널 * 49 + y * 7 + x`. `전결합1.가중치` 의
열 순서가 이것과 맞아야 한다. JS 도 같은 순서로 저장·인덱싱한다.

정규화는 `shape.json` 의 값으로 `(화소/255 - 평균) / 표준편차` 를 적용한다.

## 6. 데모 페이지 (`index.html`, `app.js`)

데스크톱 GUI 와 같은 구성으로 간다.

- 280x280 캔버스, 검은 배경 · 흰 선, 붓 굵기 18 (`draw_app.py` 와 동일)
- **포인터 이벤트**(`pointerdown` / `pointermove` / `pointerup`)로 마우스와 터치를
  한 코드로 처리한다. 캔버스에 `touch-action: none` 을 주어 그리는 중 스크롤을 막는다.
- 손을 떼면 자동 인식. `지우기` / `다시 인식` 버튼, `Esc` / `Enter` 단축키.
- 큰 숫자 + 확신도 + 상위 3후보 막대. 막대에 `█` 를 쓴다 —
  cp949 제약은 파이썬 CLI 전용이고 브라우저는 유니코드를 처리한다.
- 빈 캔버스면 인식하지 않는다 (`draw_app.py` 의 표준편차 검사와 같은 취지).

`draw_app.py` 는 tkinter Canvas 와 PIL 이미지에 **이중으로** 그려야 하는 제약이 있지만,
웹은 `ctx.getImageData()` 로 캔버스를 되읽을 수 있어 단일 출처다. 이중 그리기를
하지 않는다.

가중치 적재는 약 1.7MB fetch 이므로, 끝날 때까지 "모델 불러오는 중" 을 표시하고
캔버스를 비활성화한다. 실패하면 `export_weights.py` 를 돌리라는 안내를 띄운다.

## 7. 검증 페이지 (`verify.html`)

저장소에 테스트 프레임워크가 없다. 브라우저 자체가 실제 실행 환경이므로
검증도 브라우저에서 한다. Node 설치 여부와 무관하다는 이점도 있다.

`verify_samples.json` 을 읽어 200 장에 대해:

1. 28x28 원본을 반전 → 10배 최근접 확대 → 280x280 (4.4 의 2·3번)
2. `preprocess.js` 통과 → 28x28 과 `기대_전처리28x28` 비교
3. `model.js` 통과 → `기대_로짓` 과 비교

보고 형식:

```
샘플 200 장

전처리  픽셀 최대 오차   0        (허용 1)
추론    로짓 최대 오차   3.8e-05  (허용 1e-3)
예측    일치            200/200  (허용 200/200)
정답률                  199/200  (참고용)

판정: 통과
```

전처리와 추론을 나눠 보고하므로 어긋났을 때 어느 쪽 문제인지 바로 드러난다.
`정답률`은 판정에 쓰지 않는 참고 지표다 — 모델 성능이지 이식 정확성이 아니다.

허용치를 벗어나면 첫 불일치 샘플의 인덱스와 두 28x28 이미지를 나란히 그려
눈으로 비교할 수 있게 한다.

## 10. 구현 순서

1. `git mv` 로 파이썬 파일 이동, `__pycache__` 정리, 이동 후 동작 확인
2. `export_weights.py` 작성 → `weights.bin` / `shape.json` / `verify_samples.json` 생성
3. `tensor.js` → `model.js` 순으로 작성, `verify.html` 의 추론 항목부터 통과시킴
4. `preprocess.js` 작성, `verify.html` 의 전처리 항목 통과시킴
5. `app.js` / `index.html` / `style.css` 로 데모 완성
6. `CLAUDE.md` 세 개와 `README.md` 작성

3·4 를 먼저 하고 5 를 나중에 하는 이유는, 데모 UI 가 붙기 전에 수치 정확성을
확정해 두어야 나중에 "인식이 이상한데 UI 문제인지 엔진 문제인지" 를 겪지 않기 때문이다.
